Python ETL ETLTest Automation Framework
Python + Pandas + PyTest | CSV/TXT → Raw → Operational → Curated
A practical learning and interview reference for building reusable data-quality and reconciliation tests inside Python ETL.
Prepared for: Lingam D Reddy
1. Framework Goal
The purpose of this framework is to validate data at every stage of a Python environment ETL pipeline. Python/Pandas performs scalable data comparisons and transformations, while PyTest provides repeatable test execution and assertions that mark validations as PASS or FAIL.
CSV / TXT    |    vSOURCE FILES    |  Source-to-Raw validations    vRAW LAYER    |  Raw-to-Operational validations    vOPERATIONAL LAYER    |  Operational-to-Curated validations    vCURATED LAYER    |    vPYTEST RESULTS: PASS / FAIL
2. Validation Strategy by Layer
Stage
Core validations
Source files
File/path accessibility, not empty, delimiter/columns, schema/format, record count
Source → Raw
Count reconciliation, missing/unexpected keys, schema/columns, ingestion completeness
Raw layer
Mandatory NULLs, duplicate primary keys, data types, allowed values
Raw → Operational
Transformations, filters, datatype conversions, rejected records, key reconciliation
Operational layer
NULLs, duplicates, business rules, referential/key integrity
Operational → Curated
Aggregations, derived metrics, transformations, incremental-load logic
Curated layer
Final business metrics, NULLs, duplicates, allowed values, data quality

from pydatabase connection / pd.read_sql import DataFrameclass DataReader:    def __init__(self, spark):        self.connection = spark    def read_csv(self, path, delimiter=",", header=True) -> DataFrame:        return (self.pd.read                .option("header", str(header).lower())                .option("delimiter", delimiter)                .option("inferSchema", "true")                .csv(path))    def read_txt(self, path, delimiter="|") -> DataFrame:        return (self.pd.read                .option("header", "true")                .option("delimiter", delimiter)                .option("inferSchema", "true")                .csv(path))    def read_table(self, table_name) -> DataFrame:        return self.connection.table(table_name)    def read_sql(self, query) -> DataFrame:        return self.connection.sql(query)
6. Reusable Validation Library
from pydatabase connection / pd.read_sql import functions as Fclass DataValidator:    @staticmethod    def validate_record_count(source_df, target_df):        source_count = source_df.count()        target_count = target_df.count()        assert source_count == target_count, (            f"Record count mismatch: Source={source_count}, Target={target_count}"        )    @staticmethod    def validate_not_empty(df):        assert df.limit(1).count() > 0, "Dataset is empty"    @staticmethod    def validate_nulls(df, columns):        for column in columns:            null_count = df.filter(F.col(column).isNull()).count()            assert null_count == 0, f"{column} contains {null_count} NULL values"    @staticmethod    def validate_duplicates(df, key_columns):        duplicates = (df.groupBy(*key_columns).count()                        .filter(F.col("count") > 1))        duplicate_count = duplicates.count()        assert duplicate_count == 0, (            f"Found {duplicate_count} duplicate keys for {key_columns}"        )    @staticmethod    def validate_columns(df, expected_columns):        missing = set(expected_columns) - set(df.columns)        assert not missing, f"Missing columns: {missing}"    @staticmethod    def validate_allowed_values(df, column, allowed_values):        invalid_count = df.filter(~F.col(column).isin(allowed_values)).count()        assert invalid_count == 0, (            f"{column} contains {invalid_count} invalid rows"        )
7. Key Reconciliation
Record counts alone can pass even when the wrong records are present. A left-anti join identifies source keys missing from the target and target keys that are unexpected.
class Reconciliation:    @staticmethod    def validate_key_reconciliation(source_df, target_df, key_columns):        source_keys = source_df.select(*key_columns).distinct()        target_keys = target_df.select(*key_columns).distinct()        missing = source_keys.join(target_keys, key_columns, "left_anti")        unexpected = target_keys.join(source_keys, key_columns, "left_anti")        missing_count = missing.count()        unexpected_count = unexpected.count()        assert missing_count == 0, (            f"{missing_count} source keys are missing from target"        )        assert unexpected_count == 0, (            f"{unexpected_count} unexpected keys found in target"        )

13. How an Assertion Fits
source_count = source_df.count()target_count = target_df.count()assert source_count == target_count, "Count mismatch"
The Spark code calculates the actual result. The assertion is the final checkpoint. If the condition is True, the test passes; if False, PyTest reports a failed test and displays the message.

Run tests from Python environment workspace test tooling where available, or execute pytest in your project workflow.

16. Framework Improvements for a Real Project
Make validations configuration-driven using JSON/YAML or control tables.
Capture failed record samples to an audit Delta table instead of only returning a count.
Add batch_id/load_date filters so validations compare the correct incremental load.
Add datatype and schema comparison from table metadata.
Add referential-integrity tests between fact and dimension/business tables.
Write execution metadata: run_id, pipeline, layer, test_case, expected, actual, result, timestamp.
Integrate test execution into your Python environment job or CI/CD workflow.
For very large datasets, avoid collect(); compare with Spark joins, aggregates and hashes at distributed scale.

20. Sequential Execution Flow: What Runs First and Why
This section explains the framework in the exact order you should imagine it executing. Read it from Step 1 to Step 10 whenever the class, object, fixture, DataFrame, validation, or assertion feels confusing.
Step 1 - Python environment provides the Python runtime
The test starts on Python environment compute. The Python runtime named spark is the entry point used to read files, tables, and execute Spark SQL.
spark
Step 2 - PyTest provides spark through the fixture
The session fixture returns the active Python runtime. Tests and data-loading fixtures can request spark as an argument.
@pytest.fixture(scope="session")def spark():    return Python runtime.builder.getOrCreate()
Step 3 - Create the DataReader object
We create one object from the DataReader class and give it Spark. Creating the object automatically runs __init__.
reader = DataReader(connection=None)
Step 4 - __init__ stores Spark inside the object
Python automatically calls __init__(self, spark). self represents the new reader object. self.connection = spark stores the Python runtime so every reader method can reuse it.
def __init__(self, spark):    self.connection = spark
Step 5 - Read the source file
We ask the reader object to execute its read_csv method. The method uses self.pd.read and returns a Pandas DataFrame. That returned DataFrame is stored in source_df.
source_df = reader.read_csv(source_path)
Step 6 - Read the Raw table
The same reader object already remembers Spark, so we do not pass spark again. read_table returns the Raw table as another Pandas DataFrame.
raw_df = reader.read_table("catalog.raw.customer")
Step 7 - Data is now ready for comparison
At this point source_df and raw_df are Pandas DataFrames. Validation code works on these DataFrames using count, filter, groupBy, joins, and column expressions.
source_count = source_df.count()raw_count = raw_df.count()
Step 8 - Execute a validation
A reusable validation method receives the two DataFrames and calculates the actual values that need to be compared.
DataValidator.validate_record_count(source_df, raw_df)
Step 9 - Assertion decides PASS or FAIL
Inside the validation, assert checks the expected condition. Equal counts mean PASS. Different counts raise AssertionError and PyTest marks the test as failed.
assert source_count == raw_count, (    f"Count mismatch: Source={source_count}, Raw={raw_count}")
Step 10 - Repeat for the remaining Source-to-Raw tests
The same loaded DataFrames can be validated for mandatory NULLs, duplicate keys, expected columns, and missing/unexpected keys. This is why the reader and validation utilities are reusable.
validate_nulls(raw_df, mandatory_columns)validate_duplicates(raw_df, primary_key)validate_key_reconciliation(source_df, raw_df, primary_key)

24.14 Generic Expected-vs-Actual Comparison
def compare_columns(expected_df, actual_df, keys, columns):    merged = expected_df[keys + columns].merge(        actual_df[keys + columns],        on=keys, how="outer", suffixes=("_expected", "_actual"),        indicator=True    )    mismatch_mask = merged["_merge"] != "both"    for column in columns:        left = merged[f"{column}_expected"]        right = merged[f"{column}_actual"]        equal = left.eq(right) | (left.isna() & right.isna())        mismatch_mask = mismatch_mask | ~equal    mismatches = merged[mismatch_mask]    assert len(mismatches) == 0, f"Found {len(mismatches)} mismatches"

24.17 Important Senior-Level Choice: Pandas vs PySpark
Use Pandas when test datasets are small/medium and safely fit in memory, or for local/unit-style validation.
Use PySpark when production-scale datasets are large and should remain distributed across the cluster.
Keep the business validation pattern identical: build expected population, reconcile keys, compare expected versus actual, capture mismatches, assert and report.
For a 7+ years interview, explain the trade-off rather than claiming one is always better.
